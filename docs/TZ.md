## 2. Назначение и цели создания системы

### 2.1. Назначение

Система предназначена для приёма платежей в стейблкоине USDC за товары и услуги мерчанта. Средства переводятся напрямую из кошелька покупателя на кошелёк мерчанта.

### 2.2. Цели

1. Дать мерчанту возможность выставлять счета и получать оплату в криптовалюте без посредника, который держит деньги.
2. Автоматически определять факт оплаты и уведомлять систему мерчанта.
3. Обеспечить для покупателя оплату в несколько нажатий из распространённых кошельков: MetaMask, Trust Wallet, Phantom.
4. Исключить ошибки зачисления: двойное зачисление, зачисление чужого или неподходящего перевода.

### 2.3. Критерии достижения целей

- Оплата счёта из браузерного кошелька занимает не более 3 действий покупателя: подключить, нажать «Оплатить», подтвердить в кошельке.
- Статус «Оплачен» выставляется не позднее чем через 30 секунд после набора требуемого числа подтверждений.
- Ни одна транзакция не засчитывается более чем одному счёту (проверяется автотестами).

## 3. Характеристика объекта автоматизации

Без системы мерчант принимает криптовалюту вручную: сообщает покупателю адрес, вручную проверяет поступления в обозревателе блоков и сопоставляет их с заказами по сумме и времени. Это медленно, ошибки сопоставления неизбежны, а интеграция с сайтом магазина невозможна.

Особенности предметной области, которые учитывает система:

- в блокчейне нет «назначения платежа», и сопоставить перевод с заказом можно только по сумме, адресу и времени;
- транзакция становится окончательной не сразу, а после нескольких подтверждений;
- последние блоки могут быть заменены (реорганизация);
- комиссию сети платит отправитель в нативной монете сети (ETH).

## 4. Требования к системе

### 4.1. Требования к системе в целом

#### 4.1.1. Архитектура

Система состоит из компонентов:

| Компонент | Назначение | Технологии |
|---|---|---|
| Веб-приложение | Страница оплаты для покупателя, кабинет мерчанта | React 19, TypeScript, Vite, wagmi, viem, Reown AppKit |
| API | REST API для веб-приложения и сервера мерчанта | Node.js 22, Express 5, Zod |
| Воркер | Фоновое чтение блокчейна, подтверждения, вебхуки | Node.js, viem |
| База данных | Хранение мерчантов, счетов, очереди вебхуков | PostgreSQL 17 |
| Обратный прокси | HTTPS, раздача статики, проксирование API | Caddy 2 |

API и воркер — один исполняемый модуль с режимами `api`, `worker` и `all` (переменная `ROLE`). Схема компонентов — диаграмма Context в [DIAGRAMS.md](DIAGRAMS.md).

Серверная часть строится по слоям `domain → ports → services → infrastructure` с соблюдением принципов SOLID ([SOLID.md](SOLID.md)).

#### 4.1.2. Роли пользователей

| Роль | Возможности | Аутентификация |
|---|---|---|
| Покупатель | Просмотр счёта по ссылке, оплата | Не требуется. Идентификатор счёта (UUID v4) служит секретом ссылки |
| Мерчант | Регистрация, счета, настройки, API | API-ключ |
| Администратор | Развёртывание, конфигурация, резервное копирование | Доступ к серверу |

#### 4.1.3. Модель работы со средствами

Система **некастодиальная**:

- не генерирует, не хранит и не запрашивает приватные ключи и seed-фразы;
- не создаёт промежуточных адресов: покупатель переводит средства прямо на адрес выплат мерчанта;
- взаимодействует с блокчейном только на чтение.

#### 4.1.4. Поддерживаемые сети и токены

Токен оплаты — USDC (официальные контракты Circle). Состав сетей задаётся конфигурацией без изменения кода:

| Сеть | chainId | Тип | Подтверждений по умолчанию |
|---|---|---|---|
| Base Sepolia | 84532 | тестовая, по умолчанию | 5 |
| Ethereum Sepolia | 11155111 | тестовая | 3 |
| Polygon Amoy | 80002 | тестовая | 10 |
| Base | 8453 | основная | 10 |
| Ethereum | 1 | основная | 12 |
| Polygon PoS | 137 | основная | 32 |

#### 4.1.5. Интеграция с кошельками

Рассмотренные варианты:

| Кошелёк | Сети | Подключение к сайту | Ограничения |
|---|---|---|---|
| MetaMask | EVM, Solana | Расширение (EIP-1193, EIP-6963), мобильное приложение через WalletConnect | Для Solana нужен отдельный адаптер |
| Trust Wallet | EVM, Solana и др. | Расширение, мобильное приложение через WalletConnect | В основном мобильная аудитория |
| Phantom | Solana, EVM (Ethereum, Base, Polygon), Bitcoin | Расширение (EIP-6963 для EVM), deep links на мобильных | В мобильном режиме через deep links поддерживает только Solana |

**Принятое решение:** не привязываться к одному кошельку, а подключать все через библиотеку **Reown AppKit** (WalletConnect) поверх wagmi. Она даёт единое окно выбора кошелька, расширения в браузере, QR-код для мобильных приложений и более 500 кошельков. MetaMask, Trust Wallet и Phantom выводятся первыми.

Если не задан `REOWN_PROJECT_ID`, приложение работает с кошельками-расширениями через стандарт EIP-6963 без внешних сервисов.

Поддержка Solana (SPL-USDC, Phantom в режиме Solana) — следующий этап. Архитектура к нему готова: достаточно реализовать интерфейс `ChainClient` для Solana.

#### 4.1.6. Надёжность

1. Обнаружение платежа выполняется двумя независимыми путями:
   - **быстрый путь** — страница оплаты передаёт хэш транзакции сразу после её включения в блок;
   - **фоновый путь** — воркер сканирует события `Transfer` токена на адреса мерчантов с открытыми счетами, с сохраняемым курсором по блокам.
   Платёж засчитывается, даже если покупатель закрыл страницу или заплатил вручную с другого кошелька.
2. Перед переводом в «Оплачен» транзакция повторно проверяется. Если блок с ней исчез (реорганизация), счёт возвращается в «Ожидает оплаты», а курсор сканера откатывается назад.
3. Счёт истекает только тогда, когда сканер прочитал блоки со временем позже срока счёта. Задержки RPC не приводят к ложному истечению.
4. Смена статуса и постановка вебхука в очередь выполняются в одной транзакции БД (transactional outbox).
5. Вебхуки доставляются с повторами по экспоненте: 30 с, 1 мин, 2 мин и далее, до 6 часов между попытками, всего 10 попыток.
6. Ошибка одной фоновой задачи (например, недоступность RPC одной сети) не останавливает остальные.
7. Все сервисы перезапускаются автоматически (`restart: unless-stopped`).

#### 4.1.7. Безопасность

| Угроза | Мера |
|---|---|
| Перевод на другую сумму или другой токен засчитан как оплата | Сверка контракта токена, адреса получателя и точной суммы в минимальных единицах |
| Один перевод засчитан двум счетам | Уникальный индекс `(chain_id, tx_hash, log_index)` |
| Старый перевод засчитан новому счёту | Время блока должно попадать в окно счёта (не раньше создания минус 60 с и не позже срока) |
| Неоднозначность при одинаковых суммах | Уникальный хвост суммы, уникальность среди открытых счетов обеспечивается индексом БД |
| Кража API-ключа из БД | В БД хранится только SHA-256 хэш ключа |
| Подделка вебхука | Подпись HMAC-SHA256 с меткой времени, защита от повтора (окно 5 минут) |
| SSRF через адрес вебхука | Запрет адресов частных сетей и loopback, запрет редиректов |
| Перебор и DoS | Ограничение частоты запросов: 600/мин на IP для API, 20/ч на регистрацию, 30/мин на сообщение о транзакции |
| Перехват трафика | Только HTTPS (Let's Encrypt через Caddy), заголовки безопасности (helmet) |
| Некорректный ввод | Валидация всех входных данных схемами Zod |
| Открытая регистрация в продакшене | Флаг `ALLOW_REGISTRATION=false` |

#### 4.1.8. Производительность

- Ответ API на чтение — не более 300 мс (без учёта сети) при 1000 открытых счетов.
- Цикл воркера — раз в 5 секунд (настраивается), до 500 блоков за один запрос `eth_getLogs` (настраивается под лимиты RPC).
- Минимальные требования к серверу: 1 vCPU, 1 ГБ RAM (для сборки — 2 ГБ или swap), 10 ГБ диска.

#### 4.1.9. Эргономика и дизайн

- Интерфейс в духе титульного меню игры: тёмный тёплый фон, лучи света сверху, плывущие огоньки, белый светящийся текст, меню по центру с орнаментом у выбранного пункта. На странице оплаты акцент — сумма, где уникальный хвост визуально отделён от основной суммы.
- Меню управляется мышью и клавиатурой (стрелки, Enter, Escape — назад).
- Адаптивность от 360 px, без горизонтальной прокрутки страницы.
- Видимый фокус клавиатуры, поддержка `prefers-reduced-motion`, контраст текста не ниже WCAG AA.
- Язык интерфейса — русский. Все тексты вынесены в один модуль для перевода.
- Сообщения об ошибках говорят, что случилось и что делать.

#### 4.1.10. Масштабируемость и расширяемость

- Новая EVM-сеть добавляется одной записью в реестре сетей и переменной `CHAINS`.
- API и воркер могут работать отдельными процессами. Выдача вебхуков защищена от двойной отправки арендой записи (`FOR UPDATE SKIP LOCKED`).
- Новая фоновая задача регистрируется без изменения цикла воркера.

## 6. Порядок контроля и приёмки

### 6.1. Виды испытаний

1. **Автоматические:** `npm test` в `server/` — юнит-тесты домена и сценарии платежа.
2. **Интеграционные:** API и воркер на реальном PostgreSQL и локальной EVM-цепи (Hardhat) с тестовым токеном.
3. **Приёмочные:** ручная проверка на тестовой сети Base Sepolia реальными кошельками.

### 6.2. Приёмочные сценарии

| № | Сценарий | Ожидаемый результат |
|---|---|---|
| П-1 | Открыть магазин, сохранить ключ, войти по ключу | Кабинет открыт, ключ показан один раз |
| П-2 | Создать счёт на 10 USDC | Ссылка, сумма вида `10.00xxxx` |
| П-3 | Оплатить через MetaMask (расширение) | Статусы «Подтверждается» → «Оплачен», вебхук `invoice.paid` с верной подписью |
| П-4 | Оплатить с телефона через Trust Wallet по QR | То же |
| П-5 | Оплатить через Phantom (EVM, Base Sepolia) | То же |
| П-6 | Отправить точную сумму вручную, не возвращаясь на страницу | Счёт оплачен фоновым сканером |
| П-7 | Отправить сумму без хвоста (10.00) и передать её хэш | Отказ `NO_MATCHING_TRANSFER`, счёт не оплачен |
| П-8 | Повторно передать хэш уже засчитанной транзакции для другого счёта | Отказ, счёт не оплачен |
| П-9 | Не оплачивать счёт сроком 5 минут | Статус «Истёк», вебхук `invoice.expired` |
| П-10 | Отменить неоплаченный счёт | Статус «Отменён», страница оплаты сообщает об отмене |
| П-11 | Кошелёк подключён к другой сети | Кнопка переключения сети, после неё — оплата |
| П-12 | Недостаточно USDC | Кнопка неактивна, виден баланс и ссылка на кран |
| П-13 | Вебхук-сервер отвечает 500 | Повторные попытки с увеличением интервала |
| П-14 | Страница оплаты на телефоне 375 px | Всё помещается без горизонтальной прокрутки |

Система принимается, если все сценарии П-1 — П-14 выполнены и автотесты проходят.

## 7. Требования к вводу в эксплуатацию

1. Развернуть стек командой `docker compose up -d --build` по инструкции [DEPLOY.md](DEPLOY.md).
2. Получить `REOWN_PROJECT_ID` и добавить домен в разрешённые.
3. Создать магазин и закрыть регистрацию (`ALLOW_REGISTRATION=false`).
4. Настроить ежедневное резервное копирование БД.
5. Для работы с реальными средствами: переключить `CHAINS` на основные сети, задать собственные RPC, проверить требования законодательства о виртуальных активах в юрисдикции мерчанта.
